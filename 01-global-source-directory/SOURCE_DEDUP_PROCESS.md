# 来源查重与确认流程 / Source Deduplication Process

本文件定义：两个来源条目什么时候算"同一个来源"、如何确认、如何合并。与案例去重（CASE dedup）的原则一致：**AI 只提出判断和依据，合并必须经负责人确认；错误合并比暂时重复更难修复。**

## 1. 什么时候算"同一来源"

按证据强弱分三级：

### A 级：强证据，可判同一来源

满足以下全部：

- **同一运营主体**（同一机构、法师或编辑团队）；
- **同一发布平台**（同一域名、同一刊名刊号、同一频道 ID）；
- **同一连续出版物身份**（刊物的不同期号不算不同来源；网站改版不算新来源）。

例：两个对话窗口分别登记了 purelanders.com 的 testimonies 栏目 → A 级同源。

### B 级：需要区分的"相似但不同"

- **系列与单集**：《念佛感应录》系列 与《念佛感应录（三）》→ 父子关系，不是重复。父条目记录系列，子条目记录单集，用 note 互相关联。
- **同名不同载体**：《净土》杂志（纸本）与 净土杂志新浪博客（镜像）→ 不是重复，是原始来源与镜像的关系，各自保留，标注关系。
- **同一机构的不同出版物**：台中莲社 与《明伦月刊》→ 机构与刊物，两个来源，标注从属。

### C 级：明确不算重复

- 转载站与被转载站（这是来源链/传播关系，不是重复）；
- 同一案例的不同报道（案例层去重，不是来源层）；
- 同一来源的不同语言版本（记为关联版本，是否合并由负责人逐案定）。

## 2. 确认流程（每个疑似重复对）

1. **列差异**：把两条记录的全部字段并排，标出一致项与矛盾项。
2. **找外部证据**：核实当前可用的 URL、运营者、出版信息。AI 可以做网页核查，但核查结论必须附上所见的页面证据。
3. **给判断**：`same_source` / `alias_of` / `related_not_duplicate` / `insufficient_evidence`，并写明依据。
4. **负责人确认**：AI 的判断只是建议；负责人在 `REVIEW_NEEDED.md` 逐项确认后才执行合并。
5. **合并不删除**：合并时保留所有历史编号为别名（t01_source_id 永不删除），在 `source_id_map.csv` 中把被合并条目标记为 `merged_into:SRCxxxx`。

## 3. URL 现状与补录规则

**已核实的事实（2026-09-21）：** 恢复的四份 T01 导出文件中 URL 数量为零。GPT 当时实际使用的 URL 目前没有直接记录。

URL 的三条找回路径，按优先级：

1. **GPT 对话原文**（等全量导出 zip）：对话中提到的 URL 可逐条提取回填；
2. **已有的两份对话记录**（`notes/chatgpt_transcripts/`）：2026-09-15 的对话含有约 20 个主要来源的 URL，可立即回填；
3. **逐源现场核实**：任何来源进入详细处理前，必须先核实当前可用 URL 并写入注册表。

**规则：** 未核实 URL 的来源，`review_status` 不得标为 `verified`。注册表条目在 URL 核实前一律视为"待核实线索"，不是已确认来源。

## 4. 记录格式

每次查重判断写入注册表对应行的 `notes`，格式：

```text
dedup: {判断}; basis: {依据简述}; evidence: {URL或文件}; reviewed_by: {确认人}; date: {日期}
```

未经 `reviewed_by` 确认的判断不得执行合并。
