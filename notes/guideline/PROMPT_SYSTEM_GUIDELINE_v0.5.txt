v0.5｜七个核心 Prompt + 执行级定义 + 语料候选蒸馏法
更新日期：2026-09-24
本版目的
把此前关于叙事、教理、选题、置信度与 Pilot 的讨论重新收束为一份长期可用的总体 guideline。主线只有一条：识别哪些高价值信息值得从大量语料中蒸馏出来，并让它们分别改善明确的 Prompt。认识论与教理模型保留为硬护栏，不再占据主任务。
这份文件不是最终产品 PRD，也不是一次性 Prompt 文案。它定义的是“哪些 Prompt 存在、各自解决什么问题、吃什么输入、产出什么、哪些蒸馏物值得建设，以及以后如何一个一个验证和扩充”。
v0.5 更新重点：完成 v0.4 未完成的“执行级清晰化”，并正式加入大语料候选蒸馏法：AI 大量阅读与检索 → 推荐高信息量候选 → 人工标注 Good / Bad / Mixed → AI 从已标注正反例中蒸馏规则 → 写回具体 Prompt → A/B 验证。

一、项目目标与当前问题
项目要把散落在古籍、现代杂志、网站、法师讲法、来信与问答中的净土念佛 / 往生感应案例，整理成可检索、可阅读、每条结论可追溯来源的公开资料库，并进一步服务法师与内容创作者。
现有流水线已经能稳定完成“分段 → 事实抽取 → 去重 → 白话译述 → 创作角度 → 事实 / 版权检查 → 发布包”，并通过小规模验收。当前瓶颈不再是“AI 会不会把古文转成结构化数据”，而是：
网站 CASE 正文虽然忠实，但常常不够好看：开场千篇一律，最有力量的事实被埋在履历和出处说明之后。
术语对普通读者仍不够友好。
创作角度过于模板化，同一个“名号持诵 / 信愿念佛”标签可以套到大量 CASE，不能体现单个案例真正独特的内容价值。
AI 评分表本身仍有较多人为拍脑袋成分，尚未充分从真实语料、真实讲解方法与真实用户反应中“长出来”。
当前核心假设 大量语料的价值，不是让生成模型每次“读得更多”，也不是让 AI 自己宣布什么是“最好”。更合适的流程是：AI 先在大语料中发现和压缩候选，人从候选中标出 Good / Bad / Mixed 并说明理由，AI 再从这些经人判断的正反例中蒸馏可执行规则。最终标准仍只有一个：规则进入具体 Prompt 后，是否稳定改善输出且不增加事实、implication 或教理越权风险。
二、不可协商的共同约束
不虚构：生成内容里的事实必须绑定原文证据；缺证、矛盾、来源归属不清时不得把它写成确定事实。
不判真假：资料库记录“来源如何记载、谁如何解释”，不裁决宗教经验在外部世界是否客观发生。
教理不得由个案反向立法：CASE 可以例示、见证、提出问题，但不能凭单一或重复案例重新定义经典与祖师教义。
版权分层：古籍、公版祖师资料可以充分使用；在世法师的讲稿、现代出版物与网站材料按授权和合理使用边界处理。
AI 不自治：同一 CASE 判定、重要教理解释、正式发布规则等关键判断必须保留人工审核。
叙事可重排，但意义不能偷渡：顺序、详略、标题、节奏可以编辑；新增因果、心理、评价、动机、感官细节与确定性属于硬性禁止。
三、总体架构：一套证据底座，七个 Prompt，不同蒸馏物各司其职
七个 Prompt 不是七个互不相关的聊天模板，而是建立在同一 CASE / Evidence 底座上的不同工作角色。最重要的原则是：不要把所有蒸馏信息喂给所有 Prompt。每一种中间知识都必须回答“它具体改善哪个 Prompt 的哪一种判断？”

关键边界
P1 是“把 CASE 本身讲好”；P3 是“这个 CASE 值得讲什么”；P4 是“选定这个问题以后怎样讲”；P5 是“整个资料库接下来值得做什么”。这四个任务不能混成一个万能 Prompt。P2 提供忠实审计层；P6 负责质量判断；P7 是所有公开输出的硬性安全门。
四-A、核心对象与术语：执行级定义
这一节专门解释后文反复出现、但容易“看懂名词却不知道怎样执行”的对象。以后 Prompt、数据模型或蒸馏物出现这些词时，默认采用这里的含义。
对象 / 术语
执行级定义
最小例子 / 判断方式
Claim / Evidence Span
Claim 是来源明确支持的一条“原子事实陈述”；Evidence Span 是原文中直接支持该 Claim 的具体词句。所谓“核验”只确认来源确实如此记载，不判断宗教经验在外部世界是否真实。
原文“其子梦莲华” → Claim：“其子梦见莲花” → Evidence Span：“其子梦莲华”。不能抽成“本人梦见莲花”。
Attribution（归属）
记录一个陈述是谁说、谁看见、谁听见、谁转述以及来源作者如何记载。生成时必须保留这层距离，不能把“有人报告 X”自动升级成“X 客观发生”。
“家属称闻到异香”可以写“据记载，家属当时闻到异香”，不应改成“屋里确实充满异香”。
Narrative Method
从优秀 / 失败案例叙述中提炼出的“可执行编辑动作”。一条合格方法必须说明何时使用、具体怎么改、不能越过什么边界，并最好有好 / 坏对照片段。
不是“写得生动”，而是“若原文先列长履历、核心事件在后，可把核心事件前置；履历只保留理解事件所必需部分；不得借前置新增因果”。
Salience / Relevance
判断 CASE 中哪些事实应优先占用读者注意力。它不是“越神奇越重要”，而是综合理解必要性、叙事张力、证据清晰度与误导风险。
“临终前三日主动交代某事”可能比籍贯履历更值得前置；但一个来源归属含混的瑞相，即使很吸引人也未必适合做标题。
Question Node / Question Library
把“大主题”拆成真实读者会问的具体问题，并尽量保存原始问法、来源、语境与可证实的隐藏担忧。不同问题不能因为共享关键词就合并。
“一心不乱”至少可拆成：“有妄念是否不能往生？”“一心不乱是否等于完全无杂念？”“散乱念佛是否有意义？”
CASE Use（案例用途说明）
当系统说“这个 CASE 适合讲某问题”时，必须说明：①哪条具体 Claim 触发关联；②它能帮助说明问题的哪一部分；③不能据此推出什么；④是否存在祖师 / 法师历史上曾这样使用。relation type 只是简短检索标签，不是主要知识。
问题“没有瑞相是否等于没有往生？”：某 CASE 未记录瑞相，可用于提出 / 对照这一问题；但不能仅凭“无瑞相记载”证明其一定往生或一定不往生。
Doctrinal Position
把“经典、祖师、后世法师分别怎么说”分层保存，而不是让 AI 合成一个无来源的统一答案。每个 Position 都应有出处、适用范围和与其他解释的关系。
经典文本描述 X；祖师 A 对 X 作解释 Y；法师 B 引祖师 A 处理现代问题。三层分别记录，不压成“净土宗认为 Y”。
Teaching Method / Teaching Path
面对一个具体困惑，优秀讲者把听众从“起始误解 / 焦虑”带到“更准确理解”的一串认知动作。它研究的是怎样纠正具体推论，不是“联系生活、深入浅出”这种风格词。
“有妄念→不能往生”：先识别真正焦虑 → 找出跳跃推论 → 引入最少充分教理 → 用 CASE 例示现实处境 → 明确 CASE 不证明教理 → 防止滑到“所以随便念也行”。
Audience Need / Job-to-be-done
描述用户此刻来完成什么任务，而不仅是其身份。身份可相同，任务不同，所需内容也不同。
同一名念佛人可能此刻只是想读故事，也可能在病中寻找理解，或正在准备一场分享；三个场景需要的内容层不同。
Failure Pattern
可重复出现、能够具体指出“为什么这个输出不好”的失败模式。它必须能落到文本行为，而不是“感染力不足”这样的抽象评价。
“开头连续交代出处、籍贯、履历，核心事件到第三段才出现”是可观察失败；“不够精彩”不是。
Quality Rule / Pairwise Preference
Quality Rule 是从好 / 坏对照与真实反馈中抽出的可观察规则；Pairwise Preference 是让人直接比较 A/B 哪个更好，而不是先强迫打绝对分。
规则：“专门术语首次出现时是否给出最低限度解释”；A/B 测试再看目标读者是否稳定偏好符合该规则的版本。
Implication Check
检查“所有单独事实都可能有出处，但组合后的句子是否额外增加了因果、心理、评价、动机、确定性或普遍化”。它与 Fact Check 同级。
原文只说“病重、念佛、后坐逝”，若改写成“因为精进念佛，他终于安详坐化”，就新增了因果、评价和“终于”的完成感。
执行规则：如果某个新对象无法用“它是什么 → 它具体回答什么问题 → 一个可核验例子”三步解释清楚，就暂时不要把它升级成正式蒸馏物或 Prompt 输入。
五、七个 Prompt 的详细规格
P1｜CASE Reader Narrative｜网站 CASE 读者正文
定位：主产品 Prompt；第一优先  把已经结构化并核验的单个 CASE 写成普通读者愿意读完的网站正文。
使用场景
用户点开一个案例页面，主体区域需要一篇现代、流畅、忠实的故事正文。它不是 FAQ、讲稿，也不是研究摘要。
核心输入
• CASE 原文 • 核验后的 Claim / Evidence Span：Claim 是“来源明确支持的一条原子事实陈述”，Evidence Span 是原文中直接支持它的具体词句。例如 Claim=“其子梦见莲华”，Evidence Span=原文“其子梦莲华”；核验只确认“来源确实这样写”，不判断梦境在外部世界是否真实。 • 人物、时间、地点、事件等结构化事实 • Attribution（归属）：必须保存“谁说、谁见、谁转述”。例如“家人报告闻到异香”不能被简化成“室内确实有异香”。 • 必要的术语解释与来源元数据
核心输出
• Reader-facing CASE Narrative • 必要时生成标题 / 导语候选，但不得夸大 • 可与原文 / 忠实白话译述并列展示
主要依赖的蒸馏物
• Narrative Method Library：优秀案例如何开场、重排、压缩履历、控制节奏 • Salience / Relevance Rules：什么事实在什么情况下值得前置 • Terminology & Reader Comprehension：哪些术语需要解释、怎样解释不失真 • Failure Library：常见“事实没错但不好看 / 偷偷加意义”的失败模式
边界 / 不能做
• 不能围绕某个教理问题强行改写整篇 CASE，除非产品明确进入专题模式 • 不能补心理、因果、评价、动机、感官细节、戏剧对白 • 不能把瑞相 / 个案解释升级为教义结论 • 不能因追求 hook 而提高来源本身的确定性
验收重点
• 忠实度与 Attribution 错误为 0 • Implication 错误为 0 • 核心事件不再机械埋在“出处 + 履历”之后 • 非必要履历被压缩但不丢失理解所需信息 • 术语对目标读者可懂 • 同一规则能跨多个 CASE 重复改善而非只对一个例子有效
说明：这里的“蒸馏物”是可审查、可追溯的中间知识，不是让生成模型自由吸收整个语料库。
P2｜Faithful Plain-language Translation｜忠实白话译述
定位：支撑 / 审计 Prompt；已有能力继续优化  让不懂古文或旧式文体的读者准确理解“原文按自己的顺序究竟说了什么”。
使用场景
作为原文与 Reader Narrative 之间的可审计中间层，也可供研究者、编辑和事实核查使用。
核心输入
• 原始文本（优先保留段落与句子定位） • 词义 / 人名 / 地名 / 时代术语表 • 必要的版本信息与异文
核心输出
• 忠实白话译述 • 保留原文的不确定性、转述关系和信息顺序 • 必要的术语注释，但不进行自由发挥
主要依赖的蒸馏物
• Historical / Buddhist Terminology Glossary • 古文到现代汉语的稳定转换规则 • 歧义词与常见误译 Failure Library
边界 / 不能做
• 不是为了追求“最好看”，不应为了叙事效果大幅重排 • 不能把古文含混处翻成现代语义上更确定的断言 • 不能把译者自己的教理解释混进译文
验收重点
• 信息完整且不擅自增减 • 主语、时序、引语与转述关系准确 • 术语译法一致且可解释 • 能作为 P1 与 P7 的可靠审计参照
说明：这里的“蒸馏物”是可审查、可追溯的中间知识，不是让生成模型自由吸收整个语料库。
P3｜CASE Angle Discovery｜单案例创作角度发现
定位：创作者 Prompt；第二优先  给定一个 CASE，发现“为什么这个案例值得讲、适合回答哪些具体问题”，而不是贴通用标签。
使用场景
法师、KOL、编辑查看一个 CASE，希望快速知道它最有价值的 3–5 个具体切入点。
核心输入
• 单个 CASE 的 Claim / Evidence • Question Library：真实提问与问题变体 • Doctrinal Position / Citation：相关经典、祖师、法师解释 • CASE Use Framework（案例用途框架）：不是只标“related_to”，而要说明：① CASE 中哪条具体 Claim 触发关联；②它能帮助说明问题的哪一部分；③不能从它推出什么；④是否有祖师 / 法师历史上曾这样使用。illustrates / contrasts / raises_question / historically_cited_for 等 relation type 只是便于检索的短标签。 • Audience / Job-to-be-done 信息（有则使用）
核心输出
• 3–5 个 Angle Cards • 每个角度包含：具体问题；为什么这个 CASE 特别适合；触发关联的证据 Claims；CASE Use（能说明什么 / 不能说明什么）；教理锚点；使用风险 • 拒绝输出没有 CASE 特异性的泛标签
主要依赖的蒸馏物
• Question Library / Observed Question Map • Doctrinal Question & Position Library • Audience Needs Map • CASE Use Library：保存“CASE 的哪条事实为什么能帮助讨论某问题、可承担什么作用、不能推出什么、是否存在历史用法”；relation type 只是其中一个字段 • Failure Library：模板化角度、个案越权、技术话题化
边界 / 不能做
• 不能把“名号持诵、信愿念佛、临终正念”等大词本身当成完成的角度 • 不能因为 CASE 有某现象就自动建立教理结论 • 不能凭频率把“常见问题”当成“最重要问题” • 不能为了给创作者“有东西可讲”而硬凑角度
验收重点
• 角度必须能回答一个真实、具体、可理解的问题 • 每个角度都能指出“为什么偏偏是这个 CASE”，并落到至少一条具体 Claim • 必须写清“CASE 能帮助说明什么”与“不能据此推出什么” • 法义锚点明确，CASE 只承担它能承担的作用 • 不同 CASE 的输出有明显区分度 • 创作者拿到 Angle Card 后能迅速判断是否可用
说明：这里的“蒸馏物”是可审查、可追溯的中间知识，不是让生成模型自由吸收整个语料库。
P4｜Teaching / Creator Strategy｜讲解与内容策略
定位：创作者深度 Prompt；后续  当创作者已经选定一个问题 / 角度和若干 CASE 后，规划“怎样讲、先后顺序、案例放在哪里、哪些边界必须说清楚”。
使用场景
法师或 KOL 已决定做“一定要一心不乱才能往生吗？”之类的内容，需要一个可直接用于备课 / 内容策划的结构，而不是让 AI 自由写讲稿。
核心输入
• 已选 Question / Angle • 审核后的 Doctrinal Position Map • 选定的 CASE 与 Case-use Relation • 目标受众与知识状态 • 必要的版权 / 引用限制
核心输出
• Teaching Strategy / Content Outline • “讲解路径”必须写成可观察的认知动作，而不是“联系生活 / 通俗解释”一类口号。典型结构可包括：识别听众表面问题背后的真实焦虑或隐藏假设 → 找到需要纠正的关键推论 → 只引入解决该问题所需的最少充分教理 → 决定 CASE 是否适合、放在何处、承担什么用途 → 明确 CASE 不能证明什么 → 防止听众从新解释滑向另一个极端 • 每个 CASE 在内容中的位置与用途 • 风险提醒与需要人工决定之处
主要依赖的蒸馏物
• Teaching Method Library：不是收集“深入浅出、联系生活”等风格标签，而是从真实讲稿 / 问答中提炼“面对某类具体困惑，优秀讲者如何把听众从起始误解带到更准确理解”的步骤。每条方法至少记录：起始困惑、隐藏假设 / 错误推论、讲者采取的关键动作、最小充分教理依据、CASE 的使用方式、需要阻断的反向误解、目标理解状态。 • Doctrinal Position & Citation Library • Audience Needs / Knowledge State • CASE Use Library
边界 / 不能做
• 不能让案例承担教义证明功能 • 不能替法师生成未审核的教理结论 • 不能因为“更能打动人”而剪掉必要的限定和差异 • 不能假装不同祖师 / 法脉的解释完全一致
验收重点
• 结构真正解决目标问题而非堆资料 • 每一步都能说明“它在修正哪个误解 / 回答哪个子问题”，而不是只有形式顺序 • 教理依据与案例用途分层清楚 • CASE 的作用与边界清楚：为什么此处需要它、去掉它会损失什么、它不能证明什么 • 创作者能看出每一步为什么存在 • 有明确“不可这样讲”的风险提示

P5｜Editorial Topic Discovery｜选题预选单 / Editorial Radar
定位：编辑策划 Prompt；后续  从整个案例库、真实问题语料与内容覆盖现状中发现“现在值得做什么”，帮助创作者挑题。
使用场景
编辑或创作者没有先选 CASE，而是在找下一篇 / 下一讲值得做的主题。
核心输入
• Question / Need Map • CASE 库及每个问题的案例覆盖 • 教理资料覆盖程度 • 已发布内容 / 重复度 • 受众信号与来源多样性
核心输出
• Editorial Radar：候选选题而非单一排行榜 • 每个选题显示：真实问题、需求证据、CASE 支撑量、教理资料、受众、风险、现有内容与内容缺口 • 允许并列展示“高频问题 / 基础但不热门 / 长期被忽视 / 新案例带出的议题”等不同 lane
主要依赖的蒸馏物
• Observed Question Map • Audience Needs Map • Doctrinal Coverage Map • CASE Coverage / Provenance • Editorial Diversity Rules：避免只追高反馈主题
边界 / 不能做
• 不能把“出现次数最多”自动等同“最值得做” • 不能把内容系统优化成感应奇闻 / 求福报的流量排行榜 • 不能隐藏 selection bias：公开问答、留言、来信都不是总体人口抽样
验收重点
• 选题理由透明可查 • 能看出需求与供给缺口，而非只给热度 • 能保留传统重要但不热门的基础主题 • 不会让创作者生态越来越同质化

P6｜Quality Judge / Critic｜内容质量评审
定位：评价 Prompt；与每个生成 Prompt 配套演化  判断生成结果“是否真的好”，并指出可操作的失败原因；不是简单给一个 1–5 分。
使用场景
用于 Prompt 研发 A/B、回归测试与发布前质量检查。Reader Narrative 与 Angle Discovery 应有不同的子 rubric。
核心输入
• 待评文本 / Angle Cards / Strategy • 对应原始 CASE / Claims 与该 Prompt 的任务定义 • 已人工标注的 Good / Bad / Mixed Example Library；现有 AI 输出首先视为 baseline，只有明确暴露特定失败模式的版本才标为 negative / hard negative • 当前版本的 Quality Rules • 必要时加入目标用户的 pairwise preference
核心输出
• 维度化诊断：具体哪条规则通过 / 失败 • Pairwise preference（A vs B）及理由 • 可追踪到规则的修改建议 • 长期可形成回归测试集
主要依赖的蒸馏物
• Human-labeled Good / Bad / Mixed Example Library：正例优先来自真实法师问答、祖师书信 / 开示、优秀人类案例讲述和已经人工认可的系统输出；负例包括明确失败的旧输出与真实语料中的失败片段 • Hard Negative Library：事实大体正确、语言通顺，但“就是不好用”的旧系统输出，尤其适合训练质量判断 • 从人类标注正反例中开放编码得到的 Quality Rules • 真实读者 / 创作者反馈 • Prompt-specific failure taxonomy
边界 / 不能做
• 不能用一个总分掩盖致命错误 • 不能用“文学性”“感染力”这类空泛词代替可观察行为 • 不能让 Judge 的偏好替代 P7 的硬事实检查 • 不能只让同一个生成模型自评然后视为客观结果
验收重点
• 评分 / 判断能稳定解释人的 A/B 选择 • 失败原因具体到可修改 Prompt 的程度 • Reader 与 Creator 任务分开评 • Fatal error 与软质量问题分层
说明：这里的“蒸馏物”是可审查、可追溯的中间知识，不是让生成模型自由吸收整个语料库。
P7｜Fact + Implication Checker｜事实与意义偷渡检查
定位：硬门 Prompt；所有公开生成必须通过  不仅检查“每个事实有没有出处”，还检查真实事实的组合是否偷偷增加了来源没有给出的意义。
使用场景
任何 Reader Narrative、白话译述、角度、讲解策略等准备进入发布 / 创作者使用链路前。
核心输入
• 生成文本 • Claim / Evidence Span • Attribution 与 Source / Provenance • 必要的教理 Position / Authority 信息 • 已审核的 CASE Use / Interpretive Guardrails：系统允许把案例当作例示、对照、提出问题、历史引用等；不得把 CASE 自动作“证明教义”的依据
核心输出
• 逐项 PASS / FAIL • 错误定位到句子与具体类别 • 建议退回生成还是人工复核 • 不得自行“修成另一个新版本”而跳过复核
主要依赖的蒸馏物
• Implication Failure Library • Attribution Rules • Doctrinal / Interpretive Guardrails • 常见强度词、因果词、心理词与泛化风险模式
边界 / 不能做
• 不能只查名词、数字、时间等显性事实 • 必须识别“因此 / 终于 / 果然 / 他意识到 / 证明了 / 一定”等可能提高因果、心理、评价和确定性的表达 • 必须检查 CASE → DOCTRINE 的越权推断 • 不得把“重复出现”写成对超自然事件的外部科学证明
验收重点
• 事实错误 = 0 • Attribution 错误 = 0 • 新增因果 / 心理 / 评价 / 动机 / 确定性 = 0 • 个案普遍化与教理越权 = 0 • 所有失败均能回指具体 Evidence 或 Guardrail
说明：这里的“蒸馏物”是可审查、可追溯的中间知识，不是让生成模型自由吸收整个语料库。
六、蒸馏层：应该建设什么，以及分别服务哪些 Prompt
“蒸馏物”不是一个统一的大知识库。它必须有明确用途，并且只在能改善某个 Prompt 时才值得长期维护。后文对象默认采用“四-A”的执行级定义。重要的是：蒸馏不等于让 AI 读完大量资料后直接给结论；标准流程是先做候选发现，再由人标注正反例，最后才由 AI 抽取规则。第一阶段建议采用下面的对象，而不是一次把所有东西都做全。
蒸馏物

主要服务 Prompt
第一阶段状态
Narrative Method Library
从优秀 / 失败的真实案例叙述中提炼可执行编辑动作：什么情况下从事件切入、履历压缩到什么程度、如何重排时序而不新增因果、怎样放置引语与瑞相、怎样控制结尾。输出应是“触发条件 + 编辑动作 + 禁区 + 对照片段”，而不是“更生动”。

P3, P4, P5, P7

P3 前优先建设
蒸馏物的最低合格条件
从具体语料 / 用户证据而来，而不是 AI 凭空总结。
人工审得过：对象足够小，负责人能理解“为什么有这条规则”。
可追溯：每个重要结论能回到具体 source / span / 对照样本。
类型明确：经典原文、祖师解释、当代法师解释、听众问题、编辑规则不能混为同一 epistemic status。
适用范围明确：传统 / 法脉 / 时代 / audience / corpus scope 可记录。

可更新：新语料或人类 A/B 结果可以修正，而不是一旦总结就冻结成“真理”。
六-A、大语料如何变成 Prompt 规则：候选发现漏斗
这套方法解决两个现实问题：一是团队只有一个负责人，不可能人工通读全部语料；二是不能让 AI 自己定义“什么叫好”形成闭环自证。AI 的首要角色是扩大阅读与发现范围，人类的首要角色是价值判断，AI 的第二角色才是从人类标注中总结规律。
阶段
这一阶段解决什么
怎么执行
产出 / 不允许做什么
1｜AI 大量阅读与候选发现
解决“人不可能读完整个 corpus，好的讲法 / 叙事可能藏在哪里”。
围绕一个明确 Prompt 任务让 AI 扫描大量语料。例如 P1 只找“案例怎样被讲好”的片段；P4 只找“某类困惑怎样被一步步讲清”的片段。要求返回原文片段、出处、上下文和“为什么值得看”。
产出候选，不产出最终规则。AI 此时可以说“可能值得看”，不能说“这就是黄金标准”。
2｜AI 去重、聚类与压缩
解决“候选仍然太多，负责人审不过来”。
把高度重复、同一转述链、同一种讲法的片段聚类；故意保留不同风格与边界样本，如：教理严谨但难懂、很温暖但推论过头、案例使用极好、明显模板化等。
把几百 / 上千片段压缩成约 20–100 个高信息量候选；不得只留下 AI 自己最喜欢的一种风格。
3｜人工标注 Good / Bad / Mixed
解决“什么叫好必须有人的判断，而不是模型自我评价”。
负责人快速标注：Good = 值得学习；Bad = 明确不希望系统复现；Mixed = 部分很好但某处有风险。每条只需写 1–3 句理由，最好指出具体文本行为。
形成第一批 gold / negative / mixed examples。现有 AI 输出只是 baseline；只有已识别失败原因的才进入 negative / hard negative。
4｜AI 从已标注正反例中蒸馏
解决“人的判断如何变成可复用 Prompt 规则”。
让 AI 比较 Good vs Bad / Mixed：哪些可观察动作反复区分两组？把规律写成“触发条件 + 动作 + 边界 + 好坏对照片段”，并绑定来源。
产出候选 Narrative Method / Teaching Method / Quality Rule；不得只写“更生动、联系生活、法义贴合”等空话。
5｜写回 Prompt 并做 A/B
解决“蒸馏到底有没有实际价值”。
只把已审核规则写入对应 Prompt，用同一输入与旧版对打；两版均过 P7，随后由负责人 / 目标用户做 blind pairwise preference。
只有跨多个样本稳定改善，才进入正式 Prompt Library；无效规则删除，避免知识库越建越大。
关于“好例子”的来源
第一批正例不要求人工事先全部找齐。AI 可以从大语料中推荐候选，但负责人必须看到原始片段后再确认。优先级建议：真实法师问答 / 讲稿（遵守授权）与祖师书信 / 开示 → 优秀的人类案例叙述 → 项目中已经人工认可的 AI 输出。AI 自己新生成的“理想范文”可以做探索候选，但不宜在未经外部验证时直接成为 gold standard。
关于现有 AI 输出
现有输出首先是 baseline，而不是默认“坏例子”。其中已经明确出现“出处 + 履历开场机械”“角度可套所有 CASE”“技术上相关但创作者无法使用”等问题的版本，可以标为 negative；那些事实基本正确、文字也顺，但仍明显不好用的版本尤其有价值，属于 hard negative。若旧输出中有局部或整篇表现很好，也应作为正例或 Mixed 保存。
为什么 Mixed 样本很重要
真实高质量判断往往不是整篇“全好 / 全坏”。例如一个回答可能前半准确识别了听众焦虑，但结尾为了安慰而推论过头；一个 CASE 叙事可能开头很好，但把“家属报告闻香”写成了“室内出现异香”。Mixed 能帮助 AI 学到“保留什么、禁止什么”，通常比简单正负标签更有价值。
冻结方法：AI 可以大规模发现“候选好例 / 坏例”，但第一轮不要让 AI 自己生成黄金范文，再用自己的范文总结规则。那会形成闭环自证。
七、认识论与教理护栏：四层模型放在正确的位置
此前关于“莲台、坐化、品位判断、瑞相重复性”的讨论应保留，但它的主要用途是约束 P3 / P4 / P5 / P7 的推断，不是当前主线本身。建议统一采用下面四层：
层
核心问题
系统应保存什么
1 Source Evidence
来源真的这样写了吗？谁说的？第一手还是转述？
原文、版本、出处、provenance、attribution、证据 span
2 Phenomenon
材料实际报告了什么现象？
“香气 / 托梦 / 莲台 / 坐化 / 预知时至”等中性观察，不先解释
3 Doctrinal Authority
经典、祖师、后世法师如何解释相关教理？
权威层级、引用、解释范围、差异
4 Interpretive Inference
凭什么把现象 P 与教理命题 D 联系？推断有多远？
推断链、直接 / 间接依据、歧义、替代解释、解释支持度
关键区分 1｜教理权威 ≠ 历史证据强弱。现代第一手报告可能在“谁这样说过”上很直接，但不能因此重新定义往生条件。
关键区分 2｜重复性 ≠ 外部真实性证明。大量独立案例重复出现某种瑞相，可以提高“这是净土文献中稳定、广泛出现的报告类型 / 母题”的把握，但资料库仍不对超自然事件作外部科学裁决。
关键区分 3｜高频 ≠ 高诊断性。某现象出现得多，不代表它足以区分具体品位；推断强度还取决于经典直接性、祖师解释、provenance 独立性、歧义和推断距离。
冻结原则
CASE MAY ILLUSTRATE; CASE MUST NOT SILENTLY LEGISLATE DOCTRINE。案例可以例示、见证、提出问题；教理结论应回到经典、祖师与有依据的解释。
八、七个 Prompt 之间的数据边界
以后开发时，最容易再次跑偏的地方，是把某个 Prompt 的任务偷偷塞进另一个 Prompt。以下边界建议直接作为研发规则。
P1 Reader Narrative 与 P2 忠实白话译述都从同一 Evidence / Claim 层生成；P1 不应从 P2 的译文再自由二次发挥。
P1 的任务是“讲好 CASE”，不是“回答一个 FAQ”。Question Library 主要服务 P3–P5；只有在术语解释和越界防护时才轻量影响 P1。
P3 只负责“发现角度”，不负责完整写讲稿；否则无法判断角度本身是否有价值。
P4 假定角度已经选定，再规划如何讲；它不应该重新做一遍 P3。
P5 从全库发现选题，不应该把某个单 CASE 的神异程度当成“值得做”的代理变量。
P6 是软质量判断；P7 是硬约束。P6 认为“很好看”不能覆盖 P7 的 FAIL。
任何 Prompt 都不能绕过原始 Evidence / Source 直接把上一层 AI 的自由文本当作事实真源。
九、以后如何一个一个解决：单 Prompt 五步迭代法
不再一次建设完整“质量智能系统”。每次只选一个 Prompt，做一个小实验，证明有效后再扩展。不同 Prompt 使用不同语料；不要用“一心不乱”的问答语料去训练网站叙事，也不要用优秀叙事样本去决定全库选题。
Step 1｜固定任务与 baseline
选 5–10 个真实样本，冻结当前 Prompt、输入结构和当前输出。旧输出不自动等于坏例，它们是 baseline；只把已确认的失败版本标成 negative / hard negative。明确本轮只改善一个问题，例如 P1 的“开场和信息顺序”。
Step 2｜让 AI 大量阅读，只做候选发现与压缩
只扫描能回答该 Prompt 问题的语料。P1 收“案例怎样被讲好 / 讲坏”；P3 收真实问题、CASE 实际用法与教理连接；P4 收“具体困惑如何被讲清”。AI 返回候选原文、出处、上下文、推荐理由，并去重聚类，把大 corpus 压缩到负责人审得动的规模。
Step 3｜人工标 Good / Bad / Mixed，再让 AI 蒸馏规则
负责人从候选中快速标注正例、负例与混合例，并写极短理由；AI 再比较正反例，提炼“触发条件 + 可执行动作 + 边界 + 对照片段”。只有经人工审核的规则才进入候选蒸馏库。
Step 4｜把已审核规则写入新版 Prompt
不要把全部 corpus 喂给生成模型。只加入已经过人工审核、能转成明确指令、few-shot 或结构化输入的少量规则，并保留规则版本。
判断“蒸馏成功”的唯一标准
不是 AI 总结得多漂亮，而是：某条蒸馏规则进入 Prompt 后，在多个样本上稳定改善输出，同时没有提高事实 / implication / 教理越权风险。
Step 5｜A/B + P7 硬检查 + 人类选择
旧 Prompt 与新 Prompt 用同一输入对打；两版先通过 P7，再看负责人 / 目标用户是否稳定偏好新版。有效规则进入 Prompt Library；无效规则删除或退回候选层。若新版只是“更像 AI 喜欢的文本”而没有人类偏好或任务效果改善，则不算成功。
十、当前 Roadmap：保持主线，一次只展开一个 Prompt
下面是建议顺序。它不是永久锁死的产品路线，而是防止我们再次同时展开太多理论问题。P7 作为硬门贯穿所有阶段，不等待“轮到它”才使用。

十一、下一步只做什么
下一步：P1 CASE Reader Narrative vNext 1）冻结 5–10 个现有 CASE 与当前 P1 输出作为 baseline； 2）让 AI 在授权 / 公版语料中大量检索“同类 CASE 被怎样讲述”的候选片段，并去重聚类； 3）负责人只审压缩后的候选，标 Good / Bad / Mixed 与极短理由； 4）AI 从已标注正反例中蒸馏 Narrative Method / Salience / Terminology 规则； 5）写入 P1 vNext，对同一 benchmark 做 A/B，并同时跑 P7。 本阶段不要求先建完整教理主题库，也不要求人工预先找到全部黄金样本。
本轮先不继续深化莲台 / 坐化 / 品位置信度，也不先建立完整教理主题库。那些内容作为 P3–P5 与 P7 的后续护栏，在真正需要时逐题补齐。
附录 A｜任何新 Prompt / 新蒸馏物的立项检查
这个对象明确服务哪个产品场景？
它的直接用户是谁：普通读者、修行人、法师 / KOL、编辑，还是内部审核？
它吃的是原始 Evidence、结构化 Claim、蒸馏物，还是上一层 AI 文本？若是最后一种，要警惕事实漂移。
它的输出是公开正文、内部建议、候选选题还是 PASS / FAIL？
哪些判断必须由语料蒸馏支持，而不是人工拍脑袋？
哪些判断属于硬约束，不能因“更好看 / 更有传播力”而放宽？
怎样做 A/B 才能证明它真的比旧版好？
如果这条规则不能稳定跨样本复用，是否应该只保留为 CASE-specific annotation，而不是升级成全局 Prompt 规则？
附录 B｜当前冻结的总体原则
01
Evidence first
任何公开事实、解释和推荐都必须可回到来源或已审核的中间对象。
02
One case core, multiple uses
同一 CASE 的事实核心统一；Reader Narrative、角度、创作者策略是不同视图，不维护互相漂移的多套事实。
03
Distill before generate
大语料用于发现模式；生成阶段优先使用小而强、人工可审的蒸馏物。
04
Prompt-specific intelligence
不建“万能知识库”；每种蒸馏物都必须知道自己服务哪个 Prompt。
05
Facts do not imply themselves
真实事实的排列也会制造隐含意义，因此 Fact Check 与 Implication Check 同级。
06
Doctrine above anecdote
案例可以例示，不能默默成为教义立法者。
07
Human agency remains
重要同案判断、教理发布与最终上线由人负责，AI 负责发现、整理、生成与检查。
08
Output improvement is the test
是否值得继续扩建，由真实输出、A/B 和用户 / 创作者反应决定，不由理论复杂度决定。
09
AI discovers; humans define quality
AI 可以大规模发现、聚类和推荐候选；什么值得成为 Good / Bad / Mixed 以及最终 Prompt 规则，必须经过人工判断与 A/B 验证。
