# 产品侧 AI 职责与 Prompt 规范 / Product AI Roles And Prompt Standards

本文定义第一版公开网站中三个面向用户的 AI 功能（D11）的职责边界、输入输出、禁止事项与验收标准，以及所有产品侧 prompt 必须遵守的编写规范。

数据侧 Pipeline（`09-agent-automation/`，负责把来源变成案例）已有独立的 prompt 体系，本文不重复；产品侧 AI **只读已发布数据集**，永不接触受限原文（G16）。

## 1. 三个产品侧 AI 功能总览

| 功能 | 职责 | 触发方 | 输出去向 |
|---|---|---|---|
| `theme_assistant` | 对话式选题推荐（澄清、检索解释、调整） | 法师/创作者 | 对话界面 + 选题篮 |
| `search_assist` | 搜索查询改写与同义词扩展 | 所有用户的搜索框 | 搜索执行器 |
| `dharma_commentary_draft` | 教理导读文章草稿 | 编辑（内部触发） | 审核队列，人工发布 |

选题单/提纲不由 AI 生成，由确定性模板组装（D11 注）。

---

## 2. theme_assistant / 对话选题推荐

详细交互设计见 [THEME_ASSISTANT_DESIGN.md](THEME_ASSISTANT_DESIGN.md)。此处只定义 AI 侧职责。

### 2.1 子任务划分

| Prompt ID | 子任务 | 输入 | 输出 |
|---|---|---|---|
| `theme_assistant/slot_extraction` | 条件提取 | 用户最新消息、当前 slot 快照 | 更新后的 slot JSON |
| `theme_assistant/clarification` | 澄清追问 | slot 快照 | 一句追问（纯文本） |
| `theme_assistant/rank_and_explain` | 推荐与解释 | slots、候选集（仅公开字段） | ≤5 条推荐 JSON：`case_id`、`why_relevant`、`recommended_usage`、`risk_notes` |
| `theme_assistant/refine_intent` | 反馈理解 | 用户反馈、当前 slots、当前权重 | 更新后的 slots/权重 JSON |

### 2.2 输入边界

候选集中每个案例只包含已发布字段：`case_id`、`title`、`short_summary`、`tags`、`provenance_quality`、`video_fit`、`risk_flags`、`source_citation`。**不包含**原文段落、受限摘录、内部审核备注。

### 2.3 禁止事项

1. 不得输出候选集之外的 `case_id`。
2. 不得生成候选集字段之外的案例事实（情节、人名、年代、瑞相细节）。
3. 不得回答教理问题、评价感应事件真假、比较宗派高下。
4. 不得承诺"这个案例能证明往生"。
5. 候选不足时不得凑数。

### 2.4 验收

- 评测集：≥10 个固定选题 brief，人工标注预期命中案例。
- 硬指标：库外 case_id = 0；无依据推荐理由 = 0；教理自由发挥 = 0。
- 软指标：top-5 命中率、推荐理由具体性人工评分。

## 3. search_assist / 搜索辅助

### 3.1 职责

把用户输入的自然语言查询改写为检索条件，并做受控扩展：

- 繁简转换、异体字归一（異香/异香）。
- 同义词扩展（异香 → 香气、异香馥郁；身软 → 身体柔软）。
- 专有名词识别（人名、寺名、刊名直接命中，不做扩展）。

### 3.2 约束

1. 同义词表是**人工审核过的白名单文件**，AI 只做查表映射和改写建议，不现场发明同义词。
2. 扩展后的检索权限边界与原查询相同：无权看到的内容，扩展后依然看不到。
3. 界面上必须显示"已为你同时搜索：××、××"，用户可关闭扩展。
4. AI 不接触搜索结果内容，只处理查询字符串。

### 3.3 验收

- 固定查询集（≥50 条）的改写结果人工抽检，准确率 ≥90%。
- 扩展导致的越权返回 = 0（由确定性权限层保证，不依赖 AI 自觉）。

## 4. dharma_commentary_draft / 教理导读草稿

### 4.1 职责

基于**已发布的案例事实**和**已审核的教理引用库**，生成导读文章草稿。完整流程、claim ledger 和发布门槛见 `../02-data-model/DHARMA_CASE_COMMENTARY_WORKFLOW.md`，本节只补充产品侧入口的职责。

### 4.2 发布链路（D15 决定）

```text
编辑选择案例和角度
  → AI 生成导读草稿（只用库内已审核教理引用，不做新教理发挥）
  → claim ledger 逐条机器检查（事实/教理/引文/归因/版权/隐私）
  → 项目负责人人工审事实与表达
  → 通过后发布；任何一条 claim 无依据或矛盾即阻止
```

AI、生成模型、审核人三者角色不得合并；AI 不能代替负责人签字。

### 4.3 验收

- 草稿中 unsupported 与 contradicted claim 均为 0，才允许进入人工审。
- 每条教理主张绑定已审核教理引用 ID；模型记忆不得充当教理来源。
- 发布页面必须显示：AI 辅助标注、案例出处、教理出处、审核状态。

## 5. Prompt 编写规范（产品侧通用）

所有产品侧 prompt 遵守以下规则。这些规则与数据侧 Pipeline 的原则一致（README 原则 5、9、11），在产品侧重述为可检查条目：

| 编号 | 规则 | 可检查方式 |
|---|---|---|
| PR-01 | **版本化**：每个 prompt 有独立 ID 和版本号；修改即新版，不覆盖已使用版本 | `pipeline/prompts/` 或对应目录中存在版本文件 |
| PR-02 | **契约先行**：先定义输入/输出 JSON contract，再写 prompt；validator 为确定性代码 | contract 文件存在，validator 测试通过 |
| PR-03 | **生成与检查分离**：生成模型不批准自己的输出 | 检查由独立 validator 或独立 stage 完成 |
| PR-04 | **证据接地**：输出中的一切事实性 ID（case_id、fact_id、citation_id）必须来自输入 | validator 校验 ID 属于输入集合 |
| PR-05 | **Unknown 一等**：信息不足时输出 `unknown` 或显式说明，禁止猜测填充 | 评测集中设"信息不足"用例 |
| PR-06 | **无教义创造**：不生成新教理结论；教理内容只能引用已审核教理库 | claim ledger 检查 |
| PR-07 | **最小上下文**：只传当前子任务需要的字段；受限原文绝不进入产品侧 prompt | 输入 schema 审查 |
| PR-08 | **失败可见**：失败的输出与校验结果保留在运行记录中，不静默丢弃 | 运行记录审计 |
| PR-09 | **禁止人工修补输出**：AI 输出不合格就走新版本 prompt 重跑，不手改 JSON | 运行记录中输出与导入一致 |
| PR-10 | **输出语言**：第一版面向用户的输出为中文（D7）；内部结构化字段保持英文键名 | contract 抽查 |
| PR-11 | **Provider 中立**：prompt 不绑定特定厂商特性；模型名记录在运行元数据中 | 运行记录审查 |
| PR-12 | **单职责**：一个 prompt 只做一件子任务；多功能塞进一个 prompt 需明确理由 | prompt 评审 |

### Prompt 文件模板

```text
# {prompt_id} v{version}

## Role
这个角色是谁，只对哪种子任务负责。

## Input Contract
输入 JSON 的字段与来源（必须指向已发布数据）。

## Task
一句话说明唯一任务。

## Constraints
逐条列出禁止事项（从第 2-4 节对应功能的禁止清单复制）。

## Output Contract
输出 JSON schema；unknown 的表达方式。

## Examples
至少一个正常例、一个"信息不足→unknown"例、一个"输入试图诱导越界→拒绝"例。
```

## 6. 运行记录

产品侧 AI 的每次调用记录：prompt ID+版本、输入哈希、输出、validator 结果、模型名、时间。记录不含受限原文；面向公开用户的功能只记录脱敏后的必要字段（G16）。

## 7. 新增 AI 功能的准入流程

以后想加第四个 AI 功能时：

1. 写明职责、输入、输出、禁止事项（套用本文第 2-4 节格式）；
2. 定义评测集与硬指标；
3. 经项目负责人批准后加入 D11 清单；
4. 未通过评测集不得上线。
